# Результаты ревью приложения

Дата: 2026-09-17. Проверены исходники витрины, каталога, корзины, профиля, CMS, Shopify-интеграции, локализации, SEO и CI. Это список обнаруженных проблем, а не утверждение об отсутствии других дефектов.

Приоритеты: **P1** — потеря данных/синхронизации, блокировка покупки или значительной части приложения; **P2** — функциональные, продуктовые, UI и эксплуатационные ошибки; **P3** — технический долг и пробелы проверок. Галочка означает реализованное исправление; формулировки ниже описывают исходный дефект. Открытые пункты требуют дальнейшей работы или проверки.

## P1 — исправить в первую очередь

- [x] **REV-01. Повторная доставка webhook не восстанавливает неуспешную обработку.**
  - Код: `app/api/shopify/webhooks/products/route.ts:48`, `app/api/shopify/webhooks/reviews/route.ts:61`.
  - Сценарий: событие записано, последующий вызов Shopify/БД падает → событие получает `FAILED`. Повтор с тем же webhook ID получает `P2002` и ответ `200 duplicate`, независимо от статуса первой попытки. Аналогично зависшие `PROCESSING` остаются без восстановления.
  - Исправить: отличать завершённые события от требующих повторной обработки; атомарно захватывать попытку, учитывать срок блокировки, вести attemptCount. При вынесении в очередь подтверждать доставку только после надёжного сохранения задания.
  - Проверка: первая попытка падает, повтор успешно применяет изменение ровно один раз. [Shopify: повторные доставки](https://shopify.dev/docs/apps/build/webhooks/troubleshoot).

- [x] **REV-02. Витрина запрещает покупать товары, которые Shopify разрешает продавать без положительного остатка.**
  - Код: `lib/content/catalog.ts:307`, `components/commerce/product-purchase-panel.tsx:45`, `lib/shopify/product-sync.ts:868`, `prisma/schema.prisma:275`.
  - `inventoryPolicy` сохраняется, но теряется при построении ProductSummary; доступность, выбор вариантов и CTA проверяют только `stockOnHand > 0`. Вариант с `CONTINUE` и нулём/отрицательным остатком блокируется. Также требуется учитывать отключённый inventory tracking. Отдельно `variantDetails` теряет status, поэтому неактивный вариант с остатком может выглядеть доступным до отказа cart API.
  - Исправить: единая проекция Shopify-доступности с учётом статуса, tracking и policy; использовать её в карточках, фильтрах, PDP и structured data.
  - Проверка: `CONTINUE + 0`, untracked, `DENY + 0`, inactive + положительный остаток. [Shopify: условия доступности вариантов](https://shopify.dev/docs/api/liquid/objects/product).

- [x] **REV-03. Ошибка Shopify-корзины ломает весь root layout, включая административные страницы.**
  - Код: `app/layout.tsx:126`, `lib/shopify/cart.ts:280`, `lib/shopify/storefront.ts:49`.
  - При наличии cart cookie layout ждёт `getStorefrontCartCount()` без обработки ошибки. Недоступность Shopify или ошибка cart query отклоняет общий Promise.all до отрисовки любой страницы, в том числе `/admin`. В Storefront fetch также нет прикладного timeout.
  - Исправить: изолировать необязательный счётчик от основного рендера, ограничить время запроса, отделить зависимости storefront от admin; показывать недоступность корзины без ложного утверждения, что она пуста.
  - Проверка: с cart cookie и отказом/зависанием Shopify витрина и admin продолжают открываться.

- [x] **REV-04. Inventory webhook стирает состояние несинхронизированных изменений товара.**
  - Код: `lib/shopify/product-sync.ts:1130` и определение конфликтов в `lib/shopify/product-sync.ts:1096`.
  - После обновления только остатка `pullShopifyInventory()` безусловно ставит товару `SYNCED` и очищает `syncError`. Товар с `PENDING`, `FAILED` или `CONFLICT` начинает выглядеть полностью синхронизированным, хотя его цена/описание/прочие изменения не применялись. Последующее сравнение опирается на этот статус.
  - Исправить: обновлять inventory-проекцию отдельно; сохранять состояние ожидающих commerce/editorial изменений и конфликтов.
  - Проверка: inventory webhook для товара с локальными изменениями не сбрасывает их статус и диагностическую информацию.

## P2 — каталог, покупка и аккаунт

- [x] **REV-05. Полный pull и inventory webhook записывают остаток с разной семантикой.**
  - Код: `lib/shopify/product-sync.ts:868`, `lib/shopify/product-sync.ts:1110`.
  - Полный pull берёт `variant.inventoryQuantity`, а webhook — available только выбранной локации или `levels[0]`. При нескольких складах один и тот же товар меняет доступность в зависимости от последнего типа синхронизации.
  - Исправить: определить единый Shopify-совместимый контракт остатков и применить его в обоих путях. Проверка: два склада с разными остатками; pull → webhook → pull не меняет результат без реального изменения inventory.

- [x] **REV-06. Варианту без скидки показывается скидка другого варианта.**
  - Код: `components/commerce/product-purchase-panel.tsx:56`.
  - `selectedVariant.compareAtPrice || product.compareAtPrice` и `compareAtAmount ?? product.compareAtAmount` трактуют отсутствие compare-at у выбранного варианта как повод взять цену первого варианта.
  - Подтверждено изолированным SSR-воспроизведением: первый вариант имеет 100/200, выбранный доступный вариант — 100/null; интерфейс выводит €200 и −50%.
  - Исправить: при существующем selectedVariant использовать только его compare-at, включая null. Добавить regression test переключения между вариантами со скидкой и без неё.

- [x] **REV-07. Цена карточки может не соответствовать доступному для покупки варианту.**
  - Код: `lib/content/catalog.ts:306`, `lib/content/catalog.ts:647`, `components/commerce/product-purchase-panel.tsx:45`, `components/ui/product-card.tsx:145`.
  - Карточка и price sorting используют первый по createdAt вариант, даже если он недоступен; PDP выбирает первый с остатком. Например, в каталоге €50, после открытия сразу €100. Диапазон/«от» не показывается.
  - Исправить: согласовать цену каталога, сортировку и стартовый вариант; при разных ценах показывать корректный диапазон или минимальную покупаемую цену с пояснением. Проверить sold-out дешёвый вариант и доступный дорогой.

- [x] **REV-08. Добавление без merchandiseId обходит проверку локальной видимости товара.**
  - Код: `lib/commerce/storefront-cart.ts:30`, `lib/commerce/storefront-cart.ts:50`.
  - Ветка с merchandiseId проверяет PUBLIC/UNLISTED и status. Ветка без него делает findUnique без этих условий, а при отсутствии записи всё равно обращается к Shopify по переданному handle. API принимает такой запрос; server action тоже использует эту ветку.
  - Исправить: применять одну политику доступности ко всем входам. Проверка: локально скрытый/архивный или отсутствующий товар, всё ещё опубликованный в Shopify, не обходится запросом без merchandiseId.

- [x] **REV-09. Предупреждения Shopify о корректировке корзины теряются.**
  - Код: `lib/shopify/cart.ts:119`, `app/api/cart/items/route.ts:37`, `components/commerce/add-to-cart-button.tsx:72`.
  - Мутации запрашивают `warnings`, но assertCartMutation их игнорирует. UI безусловно сообщает «добавлено» и отправляет add_to_cart на одну единицу, даже если Shopify скорректировал/не увеличил количество из-за остатка.
  - Исправить: вернуть нормализованные предупреждения и фактический результат изменения в API/UI/analytics. Проверка: повторное добавление на пределе inventory не даёт ложного подтверждения.

- [x] **REV-10. Лимит количества 10 действует непоследовательно и не объяснён в UI.**
  - Код: `app/[locale]/cart/actions.ts:18`, `app/[locale]/cart/actions.ts:59`, `components/commerce/cart-item-row.tsx:31`, `app/api/cart/items/route.ts:33`.
  - При количестве 10 и запасе >10 кнопка «+» активна, но action молча возвращает управление. Повторные add-to-cart при этом могут поднять суммарное количество выше 10, потому что API ограничивает только одну операцию.
  - Исправить: согласовать бизнес-лимит между add/update и UI либо убрать произвольный предел. Проверить переходы 9→10→11 через оба пути.

- [x] **REV-11. Изменение корзины не имеет pending/error feedback.**
  - Код: `components/commerce/cart-item-row.tsx:53`, `app/[locale]/cart/actions.ts:54`.
  - Формы +/−/remove не отображают состояние отправки или ошибку; server actions не возвращают управляемое состояние при отказе Shopify. Повторные нажатия возможны, а read-modify-write количества не атомарен для запросов из разных вкладок.
  - Исправить: pending и локальное доступное сообщение об ошибке, координация изменений строки и получение авторитетной корзины после мутации. Проверить медленную сеть, исчерпанный остаток, отказ API и параллельные вкладки.

- [x] **REV-12. Корзина молча обрезается после 100 разных строк.**
  - Код: `lib/shopify/cart.ts:72`, `lib/shopify/cart.ts:170`.
  - Обе выборки ограничены first:100 без pageInfo/пагинации, но count/subtotal относятся ко всей корзине. Невидимые позиции участвуют в оплате; поиск количества таких строк тоже не работает.
  - Исправить: обходить connection либо явно ограничить создание строк с понятной обратной связью. Проверка: корзина со 101 строкой полностью управляема, суммы объяснимы.

- [x] **REV-13. Профиль показывает неполную историю и неполные заказы без признака усечения.**
  - Код: `lib/shopify/customer-account/api.ts:118`, `lib/shopify/customer-account/api.ts:124`, `lib/shopify/customer-account/api.ts:133`, `lib/shopify/customer-account/api.ts:142`, `components/profile/shopify-profile-shell.tsx:193`.
  - Ограничения: 50 заказов, 20 позиций заказа/возврата, 5 fulfillments и 20 адресов, без pageInfo. Старые заказы и часть возвращаемых товаров недоступны; количество заказов выдаётся за полное.
  - Исправить: пагинация заказов и подгрузка деталей/возвратов, явное отображение диапазона. Проверка: 51 заказ и заказ с 21 позицией.

- [x] **REV-14. «Total spent» складывает разные валюты и не учитывает возвраты.**
  - Код: `components/profile/shopify-profile-shell.tsx:83`, `components/profile/shopify-profile-shell.tsx:194`.
  - Суммируются amount всех загруженных заказов, результат форматируется валютой первого. Например, 100 USD + 100 EUR отображаются как 200 в одной валюте. Refund/cancel status не участвует; также действует усечение REV-13.
  - Исправить: использовать авторитетную метрику с определённой семантикой либо суммы по валютам с учётом возвратов/периода. Проверить mixed-currency и refunded orders.

- [x] **REV-15. Параллельные изменения wishlist теряют товары.**
  - Код: `lib/shopify/wishlist.ts:33`, `lib/shopify/wishlist.ts:61`.
  - Read-modify-write целого metafield не использует compareDigest. Изолированное конкурентное воспроизведение на исходной функции: два успешных добавления A и B оставили только `[B]`.
  - Исправить: Shopify compare-and-set с повтором после конфликта; предпочтительно идемпотентное desired state вместо toggle. Проверка: параллельные вкладки сохраняют оба изменения. [Shopify: compareDigest](https://shopify.dev/docs/api/admin-graphql/unstable/mutations/metafieldsSet).

- [x] **REV-16. Проверка одного сердечка wishlist загружает полный профиль с заказами.**
  - Код: `app/api/wishlist/route.ts:10`, `app/api/wishlist/route.ts:30`, `lib/shopify/customer-account/api.ts:107`.
  - GET и POST вызывают тяжёлый CUSTOMER_PROFILE_QUERY ради customer.id, включая историю, адреса, fulfillments и returns. POST проверяет rate limit только после этого внешнего запроса; GET не ограничен.
  - Исправить: отдельный минимальный identity query/проверенная session projection, ограничение запросов до дорогого вызова. Проверка: toggle не запрашивает orders/addresses и не зависит от их доступности.

- [x] **REV-17. Временный сбой refresh уничтожает действующую customer session.**
  - Код: `lib/shopify/customer-account/session.ts:40`, `lib/shopify/customer-account/session.ts:72`.
  - Любая ошибка discovery, сети, token endpoint или записи новых токенов приводит к deleteStoredCustomerSession. Пользователь разлогинивается при временном 5xx. React cache дедуплицирует только один render, а межзапросной координации refresh нет.
  - Исправить: различать окончательный отказ refresh и временную ошибку; координировать ротацию по session ID и повторно читать обновлённую запись после конфликта.
  - Проверка: timeout/5xx не удаляет сессию; два одновременных refresh не приводят к её удалению или перезаписи более свежих токенов.

- [x] **REV-18. Rate limiter допускает превышение лимита параллельными запросами.**
  - Код: `lib/auth/rate-limit.ts:52`.
  - Проверка existing.count и increment разделены внутри транзакции без сериализации/условного update. Подтверждено изолированным воспроизведением конкурентного чтения: при 29/30 оба запроса получили ok, итог — 31. При одновременном создании/сбросе bucket также возможен сброс счётчика.
  - Исправить: атомарный SQL upsert/условное увеличение или корректная блокировка/serializable с retry. Проверка: конкурентный тест на PostgreSQL принимает строго не больше max запросов.

- [x] **REV-19. После удаления последнего отзыва остаётся устаревший рейтинг.**
  - Код: `lib/shopify/product-reviews.ts:317`, `app/api/shopify/webhooks/reviews/route.ts:84`.
  - При delete без product reference пересчитываются только товары, у которых ещё есть ACTIVE review. Товар, потерявший последний отзыв, не обнуляется. Если отзывов вообще не осталось, ранний return пропускает даже invalidation общего review cache. Старый rating_count используется витриной/JSON-LD.
  - Исправить: сохранять явную проекцию review→product или включать в sweep товары с прежними агрегатами; invalidation выполнять и для пустого результата. Проверка: удалить единственный отзыв товара и последний отзыв магазина.

## P2 — локализация и UI

- [x] **REV-20. Португальская страница SSR рендерится с английским словарём.**
  - Код: `lib/i18n/context.tsx:45`.
  - messages всегда инициализируется из enFlat; PT загружается только useEffect через API. Без переопределения ключа в CMS SSR содержит английский текст, затем он меняется после загрузки. При сбое API смешанный язык остаётся.
  - Подтверждено SSR исходного provider: для initialLocale=pt получено `Secure checkout`, хотя PT-словарь содержит `Checkout seguro`.
  - Исправить: передавать готовый локализованный словарь с сервера. Проверка: HTML `/pt` уже португальский без JS и при недоступном translate API.

- [x] **REV-21. Locale state не синхронизируется с навигацией назад/вперёд.**
  - Код: `lib/i18n/context.tsx:45`, `lib/i18n/context.tsx:49`.
