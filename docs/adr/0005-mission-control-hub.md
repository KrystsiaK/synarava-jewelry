# ADR-0005: Mission Control — единый хаб наблюдения на виджетном каркасе

**Date**: 2026-10-16
**Status**: proposed
**Deciders**: владелец проекта

## Context

Бизнес Synarava держится на множестве разрозненных сервисов: само приложение,
Shopify, Google (Analytics / Tag / Workspace), Railway (prod + staging),
переносимый SKU-сервис ([ADR-0004](0004-portable-sku-service-boundary.md)), n8n,
Clarity, скоро Sentry, Telegram-боты, позже Meta/TikTok, и собственно
операционка — заказы, отгрузки, фактуры. Контролировать это из десятка вкладок
одному человеку невозможно: не видно, где что сломалось и где процесс завис.

Нужна **одна диспетчерская** внутри админки, которая наглядно (как n8n: узлы и
провода, по которым «бежит электричество») показывает состояние всей вселенной и
где тонкие места. Главное ограничение владельца: **снаружи — очень просто и
наглядно, внутри — прозрачно и расширяемо, без усложнения.** Любое добавление
сервиса не должно требовать переписывания.

Ключевое наблюдение: нужный расширяемый каркас уже построен владельцем в виде
трёх публикуемых пакетов `@synarava/wiring-engine` (контракт виджета, порты,
шина сигналов, связи), `@synarava/shell-kit` (chrome и раскладка виджетов) и
`@synarava/widget-generator` (ИИ-генерация виджетов). В `visit-all` они уже
работают в бою. Строить свой фреймворк заново было бы дублированием.

## Decision

Построить **Mission Control** как **read-only агрегатор-витрину** внутри админки
`synarava-jewelry`, переиспользуя существующие пакеты `@synarava/*`. Хаб только
**показывает статус и даёт ссылки наружу** («иди сюда и сделай то-то») плюс
статичную инструкцию/промпт «как чинить»; он **ничем не управляет**.

Модель отображения ложится на существующий контракт один-в-один:

- **узел** на карте = `WidgetDefinition` (`@synarava/wiring-engine`) с портом
  статуса и визуальными хинтами (`ui.color`, `icon`);
- **связь/поток** между узлами = `SystemBinding` / `UserConnection`;
- **«электричество»** = значение сигнала на шине (`SignalBus`) → подсветка
  провода, у которого свежий поток;
- **конфигурация графа** = один `WiringConfig`-JSON **в репозитории** —
  единственный источник правды и одновременно документация; в админке он
  доступен **только для чтения**.

Границы:

- **UI-хаб** — это **модуль внутри приложения** (не отдельный сервис). Своего
  деплоя/базы/авторизации не имеет.
- **Сбор статусов и супербот-проверяльщик** — **отдельный крон-воркер на
  Railway**. Он обходит сервисы, принимает вебхуки, пишет состояние в общую
  Postgres и шлёт уведомления в Telegram со ссылкой на нужный узел хаба.
- **Хранилище состояния** — две таблицы в существующей Postgres (Prisma):
  статус узла и «последний поток» по связи. Хаб читает только их.
- **Единственный по-настоящему новый UI** — видимая канва-граф («patch bay»)
  на React Flow (`@xyflow/react`), которая рендерит узлы по `WidgetPortManifest`
  и рёбра по `WiringConfig`.
- **Финансовый трекер фактур** (авансовая → финальная по заказу, учёт и хранение
  PDF) — **отдельная фича/модуль** со своей таблицей и загрузкой в существующий
  S3 (`lib/s3.ts`). Данные вводятся вручную; портал остаётся юридическим
  источником фактур. Хабу он отдаёт один узел «Финансы» со счётчиками. В v1 не
  входит.

Breadth without complexity: вселенная может быть сколь угодно широкой, потому что
**каждый новый сервис — это тот же маленький контракт `defineWidget` + одна строка
в `WiringConfig`**, а не новый код движка. Расширяемость берётся из контракта, а
не из объёма.

## Alternatives Considered

### UI-хаб как отдельный микросервис
- **Why not**: лишние сетевой слой, вторая авторизация и деплой ради рендера
  того, что и так живёт в Next.js. UI — это модуль; отдельного процесса
  заслуживает только фоновый коллектор.

### Построить свой виджетный/плагинный фреймворк
- **Why not**: он уже есть (`@synarava/wiring-engine` + `shell-kit`). Фреймворк,
  выдуманный до трёх реальных виджетов, всегда оказывается неверным и его
  приходится переписывать. Сначала примеры на готовом контракте — потом, если
  надо, обобщение.

### Конфигурация графа в базе, с редактированием из админки
- **Why not**: теряются git-история, ревью и откат; «документация» уезжает из
  репозитория. Правка графа — редкое событие (новый сервис раз в месяц), ей не
  нужен онлайн-редактор. Файл + read-only просмотр в админке покрывает нужду.

### ИИ сам выстраивает связи между узлами на лету
- **Why not**: связи меняются редко, цена и риск ошибок автоматики высоки.
  Отложено; при сотнях плывущих связей вернёмся.

### Внешнее бухгалтерское приложение для учёта фактур
- **Why not**: новая интеграция и, при объёме, деньги. Нужен не бухучёт, а
  журнал состояний — его закрывает существующая Postgres + S3. Портал остаётся
  источником фактур.

### Хаб как панель управления (кнопки «перезапустить», «починить»)
- **Why not**: превращает витрину в пульт с правами на опасные действия и риском
  prompt-injection через данные сервисов. Read-only + ссылки наружу — безопасно
  и достаточно.

## Consequences

- **Positive**:
  - Одно окно на всю операционку; видно не только «горит узел», но и «не течёт
    связь» — тонкие места.
  - Добавление сервиса тривиально и не трогает хаб (контракт + строка конфига).
  - Максимум переиспользования: движок, chrome и ИИ-генерация уже готовы.
  - Read-only снимает класс рисков (разрушительные действия, инъекции).
  - Конфиг-как-код = живая документация системы в git.
- **Negative**:
  - Разовая монтажная возня: подключить `@synarava/*` из GitHub Packages в
    `synarava-jewelry` (реестр/токен, workspace, peer-deps: `framer-motion`,
    `lucide-react`, `clsx`, `tailwind-merge`, `zustand`).
  - Граф на мобиле читается хуже сетки карточек — нужен сворачиваемый список.
  - Часть сервисов (Clarity, Meta, TikTok) не даёт статуса по API — такие узлы
    будут «ссылка + дата последнего просмотра», а не живые.
- **Risks**:
  - **Усложнение** — главный риск. Снимается «Контрактом простоты» в
    [runbook-плане](../runbooks/mission-control-hub-plan.md) и активным ponytail:
    жёсткий бюджет зависимостей/таблиц/файлов и список запретов на каждом этапе.
  - Дрейф конфига от реальности → супербот периодически сверяет «объявлено в
    конфиге» против «наблюдается» и помечает расхождения.
  - Версии пакетов `@synarava/*` ещё 0.x → возможны ломающие изменения;
    фиксируем точные версии.
