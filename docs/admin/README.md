# Документация по админке Synarava

Четыре документа, каждый со своей ролью. Если не уверены, с чего начать —
начните с гайда.

Контракт [разрешения конфликтов каталога](./catalog-conflict-resolution-ux.md) описывает уже подключённый flow на `/admin/products`. Live Shopify round trip и оставшиеся unsupported commerce-поля отмечены в [плане задачи](../../tasks/catalog-conflict-resolution-plan.md).

## Как это связано

```
admin-guide-ru.md          ← что система должна делать
        │
        ├── test-cases-manual-ru.md        ← как это проверить руками
        └── test-cases-playwright-en.md    ← как это проверить кодом
                    │
                    └── test-plan-ru.md    ← в каком порядке это писать
```

## Главное правило разметки

**Если кейс проверяется без браузера — он не e2e.** Каталог для авторов
автотестов размечает каждый кейс по слою: Playwright берёт только то, что
без реального HTTP-цикла и реального браузера проверить нельзя (guard'ы
маршрутов, cookie, загрузка файлов, автосохранение, порядок галереи,
сквозные жизненные циклы). Валидация полей, парсинг тегов, генерация слага,
конфликты SKU — это Vitest.

## Статус

- Vitest: 92 файла, 466 тестов.
- Playwright: 10 spec-файлов, из них по админке — 2 (`e2e/admin-auth.spec.ts`,
  `e2e/admin-layout.spec.ts`, 7 тестов) плюс инфраструктура `e2e/support/`
  (фаза 1 плана — выполнена): `storageState`-логин через отдельный проект,
  фабрики данных через Prisma с очисткой по префиксу прогона, генерация
  файловых фикстур. `pnpm test:e2e:admin` гоняет только этот срез.
- Каталог: ~160 кейсов, из них 21 уже закрыт в Vitest, остальные ждут
  спеков — фазы 3–8 плана.

## Требует решения команды

`PROD-C43` — удаление последнего изображения из галереи оставляет товар
опубликованным без картинки, потому что проверка «нужна картинка перед
публикацией» стоит только в сохранении формы. Нужно решить, баг это или
задуманное поведение, **до** написания автотеста: тест закрепит то
поведение, которое в нём зафиксируют.
