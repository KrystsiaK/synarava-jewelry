# План тестирования админки Synarava

Рабочий документ: что и в каком порядке делаем, чтобы получить полноценный
автотест-комплекс на Playwright для `/admin/**`. Составлен 2026-09-08, после
завершения Shopify-alignment (Phase A) и рефакторинга god-файлов
(`docs/history/admin-shopify-refactor-2026-09.md`, фазы 1–3).

Этот файл — **план работ**. Каталоги самих кейсов лежат отдельно:

| Документ | Роль | Язык |
|---|---|---|
| `docs/admin/README.md` | индекс пакета документации | RU |
| `docs/admin/test-plan-ru.md` | ← этот файл: фазы, инфраструктура, решения | RU |
| `docs/admin/test-cases-playwright-en.md` | каталог кейсов + разметка по слоям | EN |

## 1. Где мы сейчас

### Что уже есть

- **Vitest**: 90 файлов, 463 теста. Покрывают серверные экшены, чистые
  хелперы, отрендеренные формы админки (добавлено в Phase 3 рефакторинга),
  Shopify-слой, storefront-компоненты.
- **Playwright**: 8 spec-файлов, 40 тестов — но по админке только
  `e2e/admin-auth.spec.ts` (6 тестов): гостевой редирект, happy-path логин,
  логаут, геометрия сайдбара/топбара, отсутствие горизонтального скролла.
- **Каталог кейсов**: `test-cases-playwright-en.md` — 13 разделов, ~149
  кейсов, размечены по типу и приоритету. **Ни один из них не реализован**
  в коде, кроме шести помеченных `[existing]`.

### Что сломано или устарело

Найдено при чтении каталогов против текущего кода:

1. **Инфраструктуры для e2e не существует.** Нет `e2e/support/`, нет
   `globalSetup`, нет `storageState`, нет фикстур, нет фабрик данных, нет
   очистки БД. `readEnvValue` + шесть строк логина скопированы в каждый из
   6 админских тестов. Писать 149 кейсов поверх этого — гарантированный ад.
2. **`fullyParallel: true` + общая dev-БД + отсутствие очистки.** Сейчас
   не стреляет, потому что админских тестов почти нет и они read-only. Как
   только появятся тесты, создающие товары, — начнутся гонки и флак.
3. **Статуса `UNLISTED` нет ни в одном каталоге.** Он появился в коммите
   `5ba2e83`: `workflowState` теперь `DRAFT | PUBLISHED | UNLISTED`, в
   фильтре списка есть опция `Unlisted`, `productStatusLabel` его
   возвращает, а правило «нужна картинка перед публикацией» распространено
   и на него (`if ((isPublished || isUnlisted) && !imageUrl)`). Целый
   рабочий статус без единого кейса.
4. **UI-07 / дашборд.** Каталоги обещают плитки «Pages/Products/
   Collections/Categories/Tags». В коде их три: Pages, Products,
   Collections — Categories и Tags удалены в Phase A item 4.
5. **ISS-07 ссылается на CAT-07**, которого больше нет (раздел категорий
   удалён целиком). Кейс висит с битой ссылкой на несуществующий сценарий.
6. **Нет кейсов на границы, появившиеся после рефакторинга**: department
   выбирается только из коллекций с `isPrimaryNav`; маркетинговая коллекция
   и департамент живут в одном массиве `product.collections` и путались в
   4 местах; цена/SKU/остаток берутся из варианта, а не из зеркальных полей
   товара. Это ровно те места, где рефакторинг мог что-то сломать, и ровно
   там покрытия нет.
7. **Нет npm-скриптов** для запуска только админского среза, нет CI-джобы,
   нет разделения smoke / полный прогон.

### Вывод

Каталог кейсов пересобирать почти не надо — он неплох по содержанию, его
надо **актуализировать** (пункты 3–6) и **разметить по слоям**. А вот всё,
что нужно, чтобы эти кейсы реально писались, — отсутствует полностью.
Поэтому инфраструктура идёт раньше кейсов.

## 2. Ключевое решение: какой кейс на каком слое

Главная ошибка, которую легко совершить, — тащить в Playwright всё подряд.
Из ~149 кейсов каталога значительная часть дешевле и надёжнее живёт в
Vitest. Правило маршрутизации:

| Слой | Что туда | Почему |
|---|---|---|
| **Vitest (unit)** | Чистые правила: `parseTags`, `slugify` с диакритикой, `generateCollectionCode`, парсинг характеристик, `productStatusLabel`, `sortProducts` | Мгновенно, детерминированно, БД не нужна |
| **Vitest (server action)** | Валидация полей, конфликты slug/SKU, «System pages cannot be deleted», «Product image is required before publishing», rate-limit логика | Экшен вызывается напрямую с `FormData`; UI ничего не добавляет к проверке |
| **Vitest (render)** | Наличие полей, лейблы, привязка экшена к форме, `Department` показывает только `isPrimaryNav` | Уже сделано в Phase 3; расширяется дёшево |
| **Playwright (e2e)** | Всё, что требует **настоящего браузера, настоящей навигации или настоящего сервера**: редиректы и guard'ы, cookie/сессия, загрузка файлов, автосохранение с debounce, порядок галереи, переходы статусов с проверкой на витрине, сквозные жизненные циклы | Здесь и только здесь e2e даёт то, чего не даёт нижний слой |

**Практический критерий**: если кейс можно проверить, не запуская браузер —
он не e2e. Если проверка теряет смысл без реального HTTP-цикла и реальной
БД — он e2e.

По этому критерию из каталога в Playwright уходит примерно 85–95 кейсов,
остальные либо уже покрыты Vitest'ом, либо туда переезжают. Точная разметка
— задача Фазы 2.

## 3. Фазы

### Фаза 0 — фиксация базовой линии
**Цель**: знать, от чего отталкиваемся, чтобы регрессии были атрибутируемы.

- Прогнать `pnpm exec vitest run`, `pnpm run lint`, `pnpm exec tsc --noEmit`,
  `pnpm run build`, `pnpm run test:e2e` и записать результат.
- Зафиксировать: 463 vitest-теста, 40 e2e-тестов — это точка отсчёта.
- Убедиться, что `pnpm run test:e2e` вообще проходит на текущем `main`
  (сейчас не проверялось — dev-сервер поднимается самим Playwright'ом).

**Готово когда**: все пять команд отработали, результат записан сюда.

### Фаза 1 — инфраструктура e2e ✅ **выполнено 2026-09-08**
**Цель была**: сделать так, чтобы написание нового админского теста стоило
десять строк, а не сорок.

Создан `e2e/support/`:

| Файл | Содержимое |
|---|---|
| `env.ts` | Единственная копия чтения `.env.local` → `.env` (раньше была скопирована прямо в spec). `readEnvValue`, `adminCredentials()`, `hasShopifySandbox()`. |
| `auth.ts` | `loginAsAdmin(page)`, `hasAdminCredentials()`, `ADMIN_STORAGE_STATE_PATH`, `suppressPrivacyBanner(page)` (см. ниже). |
| `auth.setup.ts` | Playwright setup-проект: логинится один раз, сохраняет `storageState`. Если кредов нет — пишет пустой валидный storageState и скипает себя, чтобы зависимый проект не падал на отсутствующем файле. |
| `factories.ts` | `createTestProduct/Collection/Page/ProductVariant`, `assignProductToCollection`, `cleanupTestData(runId)` — всё напрямую через Prisma, без UI. Собственный `PrismaClient`, не завязан на `@/lib/db`. |
| `fixtures.ts` | Расширенный `test` с фикстурой `runId` — уникален на тест, в teardown вызывает `cleanupTestData`. |
| `media.ts` | Генерация фикстур на лету: валидный 1×1 PNG, файл >10 МБ, битый `.jpg`, `.pdf` под видом картинки. В репозиторий не коммитятся — пишутся во временную директорию ОС. |

Решения:

1. **Аутентификация — `storageState`, через отдельный Playwright-проект.**
   `playwright.config.ts` теперь описывает три проекта: `setup` (гоняет
   `*.setup.ts`), `chromium` (сторонний + `admin-auth.spec.ts` — он
   тестирует сам логин/логаут, поэтому обязан стартовать неаутентифицированным)
   и `chromium-admin` (`admin-*.spec.ts`, кроме `admin-auth`, зависит от
   `setup`, стартует уже залогиненным). Будущие `admin-products.spec.ts` и
   подобные подхватятся автоматически по паттерну имени файла.
2. **Изоляция данных — префикс прогона.** Каждая сущность из фабрик называется
   `e2e-<runId>-...`; фикстура `runId` в `fixtures.ts` удаляет всё с этим
   префиксом после теста. Проверено: 0 висящих записей после прогона.
3. **Параллельность.** `fullyParallel: true` оставлен. Правило действует:
   никогда не проверять абсолютные количества в списках.
4. **Shopify.** `hasShopifySandbox()` в `env.ts` — для будущих `SYNC-*`,
   проверяет то же сочетание переменных, что и `lib/shopify/admin.ts`.
5. **Скрипт**: `test:e2e:admin` добавлен (`playwright test e2e/admin-`,
   подхватывает `setup` как зависимость автоматически). `test:e2e:smoke`
   отложен до появления реальных `@smoke`-тегов — заглушка без тестов
   бессмысленна.

**Сделано также** (то же самое «Готово когда», что и планировалось):
`e2e/admin-auth.spec.ts` переписан на новые хелперы — 179 строк / 6 тестов →
26 строк / 3 теста. Три оставшихся теста (гостевой редирект, логин, логаут)
тестируют сам механизм входа и поэтому остаются в неаутентифицированном
`chromium`. Три теста геометрии (сайдбар/топбар/оверфлоу), которые раньше
просто попутно логинились в том же файле, переехали в новый
`e2e/admin-layout.spec.ts` под `chromium-admin` — там они вообще не логинятся,
страница уже приходит с сессией.

**Найдено по пути, не входило в план:**

- **Баннер согласия на cookies перекрывает `/admin/**`.** `PrivacyConsentManager`
  примонтирован в корневом `app/layout.tsx`, то есть заявленный для витрины
  баннер согласия реально показывается и внутренним сотрудникам в админке —
  это отдельный, самостоятельный UX-баг, не связанный с тестами. Тест логаута
  падал именно на этом: баннер перехватывал клик по «Log out». Не стал чинить
  `app/layout.tsx` — это решение продукта (нужен ли админке баннер вообще), не
  моё. Вместо этого `loginAsAdmin`/`auth.setup.ts` заранее ставят cookie
  согласия (`suppressPrivacyBanner`) тем же способом, каким его ставит
  реальный админ при первом визите — это не костыль теста, а имитация
  нормального пользовательского пути.
- **Локальная БД для разработки пуста по контенту.** `Page` — 0 строк
  (включая системные `home`/`about`/`manifesto`), при этом `Product` — 7,
  `Collection` — 4. Из-за этого `/admin/home` реально рендерит `null`
  (`if (!page) return null;` в `app/admin/(studio)/home/page.tsx`) — это же
  открывшийся баг для storefront-теста `home.spec.ts` (не мой файл, не трогал).
  Ровно из-за этого выбрал для теста геометрии не `/admin/home`, а
  сгенерированную через `createTestPage` тестовую страницу — она гарантированно
  существует и достаточно длинная для проверки независимой прокрутки, вне
  зависимости от того, засеяна ли реальная БД.
- **15 из 40 storefront e2e-тестов уже красные на чистом `main`,
  без единой моей правки** (`catalog-resilience`, `commerce-analytics`,
  `home`, часть `navigation`, `product-detail`). Проверено сравнением:
  тот же прогон на оригинальном однопроектном `playwright.config.ts` даёт
  идентичные 15 отказов. Причины — тот же баннер согласия плюс пустая `Page`
  таблица. Не входит в объём этой задачи (`/admin/**`), не трогал — но стоит
  знать, что `pnpm test:e2e` без фильтра в этой среде красный независимо от
  админки.

## 4. Риски

| Риск | Митигация |
|---|---|
| **Флак из-за общей БД и параллельности** | Префиксы прогона + запрет на абсолютные счётчики (§3, Фаза 1). Если всё равно течёт — отдельная тестовая БД. |
| **Автосохранение с debounce 700 мс** | Никаких `waitForTimeout(700)`. Только `expect.poll` / `toPass` с таймаутом ~2 с. Явно записано в каталоге. |
| **Зафиксируем баг как ожидаемое поведение** | Три «Open questions» разрешаются руками до написания ассертов (Фаза 2). |
| **Тесты требуют `ADMIN_PASSWORD` в открытом виде** | Это dev-only путь (в production обязателен `ADMIN_PASSWORD_HASH`). Для CI — отдельные тестовые креды в секретах, не боевые. |
| **149 кейсов — это много, работа встанет** | Слоевая маршрутизация (§2) убирает треть в Vitest; фазы нарезаны по одному файлу, каждая самодостаточна и коммитится отдельно. |
| **Загрузка видео (VID-*) требует реального бакета** | Мокаем `/admin/api/videos` и PUT в бакет; сценарии, которые без реального бакета не проверить (VID-07), помечаем integration-only. |

## 5. Что осознанно вне охвата

- Визуальная регрессия (скриншот-диффы) — отдельная задача, не смешиваем.
- Нагрузочное тестирование админки.
- Кросс-браузерность: `playwright.config.ts` сейчас только Chromium.
  Админка — внутренний инструмент, матрица браузеров ей не нужна.
- Тестирование самого Shopify API (мы тестируем нашу интеграцию, не их API).
- E2E-покрытие витрины — уже частично есть в остальных 7 spec-файлах,
  этот план про `/admin/**`.
