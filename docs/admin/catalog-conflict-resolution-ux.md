# Разрешение конфликтов каталога: UX-спецификация

**Статус:** контракт каталога `/admin/products` реализован 23 сентября 2026. Диалоги 1–3 пишут только через scoped preview/apply. Не покрыты scoped-записью: Status, storefront visibility, category, tags, collections, media, несколько variants, characteristics — они видны как `Not included` / Unavailable. Live Shopify round trip остаётся в [`../../tasks/catalog-conflict-resolution-plan.md`](../../tasks/catalog-conflict-resolution-plan.md) этапе 7. Это описание работающего UI, а не будущего состояния.

## Задача и границы

Администратор должен заметить конфликт, понять, **какой товар, язык и поле** затронуты, увидеть обе версии до записи и осознанно выбрать итог. Первый релиз охватывает каталог товаров. После проверки паттерн можно перенести на коллекции, страницы и другие Shopify-связанные сущности.

Слово «версия Synarava» означает сохранённые данные нашей базы (Railway), «версия Shopify» — актуальные данные связанного магазина. Направление операции всегда формулируется глаголом и адресатом: «Применить Shopify в Synarava» или «Отправить Synarava в Shopify». Надпись «синхронизировать» без направления не используется для разрешения конфликта.

Массовая операция затрагивает только **перечисленные в preview конфликтующие товары и поля, для которых есть Shopify-контракт**. Она не стирает всю базу Railway, локальные editorial-поля без Shopify-аналога, другие товары или другие языки. Если конкретное поле нельзя безопасно записать в выбранном направлении, оно исключается из операции с объяснением; интерфейс не обещает «заменить всё», когда backend этого не делает.

## Сигнал на странице каталога

Рядом с заголовком «Каталог» показывается полный статус: есть ли сохранённые конфликты, свежа ли проверка, когда она выполнялась и действие `Run conflict check`. В панели над таблицей длинный статус не дублируется: там появляется только компактный янтарный вход `N conflicts`, и только когда конфликт действительно есть. Цвет заметный, но не тревожно-красный; красный остаётся для ошибки выполнения. Метки не кодируют состояние одним цветом.

Полный статус и компактный `N conflicts` открывают один и тот же список. Если проверка ещё идёт, показываются `Проверяем Shopify…` и время последней успешной проверки, но старый результат не выдаётся за свежий. Если проверка не удалась или Shopify недоступен, показываются отдельный статус и `Run conflict check`; конфликтов «0» из-за ошибки не бывает.

В таблице товара отображаются компактные метки затронутых областей: например `PT · 2 поля`, `RU · 1 поле`, `Общее · 3 поля`. Они открывают список конфликтов с фокусом на этом товаре. Это даёт ответ «что случилось» без открытия товара. Языковые метки не используют флаги стран: один язык может обслуживать несколько регионов. Полное имя языка видно прямо в диалоге и в подсказке метки.

### Языковой корешок поля

У каждой строки сравнения слева есть короткий постоянный корешок, похожий на вкладку документа:

| Маркер | Значение | Пример |
|---|---|---|
| `PT · Português` + пиктограмма языка | Значение только португальской локали | Описание товара на португальском |
| `EN · English` + пиктограмма языка | Значение английской локали | Английский SEO-заголовок |
| `RU · Русский` + пиктограмма языка | Значение только русской локали | Название товара на русском |
| `Общее` + пиктограмма связанного поля | Общее/commerce-поле, не перевод | Цена, статус, категория |

Маркер расположен **рядом с названием поля**, а не только в шапке товара. В мобильной карточке он остаётся над парой значений. Список языков, порядок, код, локализованное название и Shopify locale берутся из `StorefrontLocale`; русский уже добавлен в реестр и участвует в этом UX наравне с английским и португальским. Компонент не содержит фиксированного перечня `EN/PT/RU`: следующий зарегистрированный язык появляется без нового UI-кода. При большом количестве локалей строка товара показывает первые две метки и `+N языков`, а полный список с количеством конфликтов по каждому языку раскрывается в диалоге. Для длинных названий предусмотрен перенос строки, для длинного списка — прокрутка/поиск по языку. Подсветка выбранной стороны не окрашивает сам языковой маркер, чтобы язык не путался с направлением записи.

## Диалог 1: список конфликтующих товаров

Заголовок: `Конфликты каталога · N товаров`. Под ним — время проверки и одно предложение о том, что изменения будут применены только после просмотра и подтверждения. Список содержит товары с нерешёнными конфликтами; локализационные и commerce-расхождения одного товара собраны в одну карточку.

Карточка товара: миниатюра при наличии, название, SKU, краткое `4 поля: PT 2 · RU 1 · Общее 1`, время обнаружения/проверки и три действия. Иконки используются только вместе с доступными именами (`aria-label`), tooltip при hover/focus и понятной легендой в шапке диалога:

1. Стрелка из Shopify — `Применить Shopify в Synarava для этого товара`.
2. Стрелка в Shopify — `Отправить версию Synarava в Shopify для этого товара`.
3. Сравнение — `Посмотреть детали и выбрать по полям`.

Каждая иконка имеет touch-target минимум 44 × 44 px. `Details` открывает диалог 2. Два направленных действия сначала открывают диалог 3 с подробным preview; ни одно не пишет сразу. Если по части полей направление невозможно, превью честно указывает исключения, а действие либо ограничено разрешённым scope, либо недоступно с объяснением.

Над списком две массовые операции: `Применить Shopify в Synarava` и `Отправить Synarava в Shopify`. Под каждой видно число товаров и полей. Они не выбирают смешанные направления и не захватывают односторонние изменения, импорт новых товаров или архивирование — это отдельные существующие сценарии. Массовая операция открывает диалог 3, где перечислено **каждое** затрагиваемое поле каждого товара. При нуле подходящих товаров кнопка недоступна.

## Диалог 2: детали одного товара

Заголовок: товар, SKU и `Конфликт: PT 2 · RU 1 · Общее 1`. Строки сгруппированы по `Общее`, затем по языкам в порядке реестра; при большом числе языков доступен поиск/фильтр по языку без потери уже сделанных решений. В каждой строке: языковой корешок, человекочитаемое имя поля, две равноправные колонки `Synarava` и `Shopify`, текущее значение и при необходимости раскрываемое `Последняя совпавшая версия`. Различия длинного текста раскрываются без обрезания важных данных; пустое значение названо `Пусто`, а потенциальная очистка явно предупреждена.

Администратор выбирает победителя **для каждого конфликтующего поля** нажатием на соответствующую колонку или её radio-контрол. Выбор обозначается рамкой, галочкой и текстом `Оставить эту версию`; hover сам по себе не выбирает. Клавиатура и screen reader получают ту же структуру. Для быстрого решения есть `Выбрать Shopify для всех видимых полей` и `Выбрать Synarava для всех видимых полей`, но они только заполняют выбор и не применяют его. Если часть полей уже выбрана, переключение одной строки не сбрасывает остальные.

Футер: `Отмена` и `Продолжить к проверке` (пользовательское название merge). Продолжение недоступно, пока хотя бы одно поле в выбранном scope не получило решение. Рядом показано `Выбрано 2 из 3`. Нажатие открывает диалог 3 поверх списка; итоговое действие ещё не выполнено.

## Диалог 3: обязательный preview и подтверждение

Один компонент используется после массовой операции, действия у одного товара и ручного выбора полей. Шапка называет направление или смешанный результат: `Проверка перед применением · 3 товара / 7 полей`. Для каждого товара показаны строки `поле + язык`, две колонки `Сейчас в Synarava` и `Сейчас в Shopify`, а также явное `После подтверждения: Shopify → Synarava` либо обратное направление. Для ручного merge направление может отличаться по строкам.

В summary показано, сколько значений изменится в каждой системе, сколько будет очищено, сколько полей исключено и почему, а также что не затрагивается. Для очистки непустого значения требуется отдельное подтверждение. Длинные значения раскрываются внутри scrollable body. **Шапка и футер остаются на месте; прокручивается только тело** (`min-height: 0`, ограничение высоты viewport, собственный scroll). На мобильном две стороны становятся вертикальными блоками с явными заголовками; горизонтальная прокрутка всей модалки не нужна.

Футер: `Отмена` и конкретный `Подтвердить N изменений`. `Отмена` закрывает только preview и возвращает туда, откуда он открыт: к списку или к выбору полей, сохраняя выбор. Escape и закрытие backdrop ведут себя как отмена; во время записи закрытие отключается. После подтверждения начинается запись, а не оптимистическое удаление конфликта.

## Выполнение и результат

После подтверждения:

1. Для массовой операции закрываются preview и список; каталог показывает спокойное состояние `Применяем изменения…` с прогрессом по товарам. Для ручного решения preview и детали закрываются, но список остаётся; соответствующая карточка показывает `Применяем…` и недоступные действия. В обоих случаях можно однозначно понять, что операция ещё идёт.
2. Сервер повторно проверяет идентичность магазина, область записи и актуальность сравниваемых версий. Если данные изменились после preview, запись этого поля останавливается и UI предлагает обновить сравнение.
3. Успех показывается только после проверки результата. При ручном решении успешно закрытый товар исчезает из списка; список остаётся открыт для следующего. При массовой операции каталог показывает summary успеха. Частичный успех перечисляет успешные и неуспешные товары; неуспешные остаются конфликтами. Ошибка не превращается в «успех» из-за закрытых модалок.

После успешного `Shopify → Synarava` строка товара получает **отдельный** маркер `Обновлено из Shopify · не просмотрено` — маленькую нейтрально-золотую точку/иконку глаза с текстовой подсказкой, без янтарного знака конфликта. Он хранится на сервере для конкретного администратора и конкретной версии товара. Исчезает только после того, как администратор открыл детали товара **после** обновления; простой просмотр списка или наведение не считаются прочтением. Новое входящее обновление возвращает маркер. Для `Synarava → Shopify` такой маркер не ставится: локальная версия не менялась. История изменения остаётся доступной после снятия маркера.

## Состояния и безопасность

- Повторная проверка при открытии списка нужна, если сохранённый результат устарел; прошлые метки помечаются временем. Нельзя выдавать локальный `syncStatus` за свежий факт о Shopify.
- Пока есть несохранённые изменения в редакторе товара, применение конфликтного решения запрещено до сохранения или выхода из черновика.
- Сервер принимает IDs и решения, но сам загружает значения и проверяет fingerprints/актуальный Shopify digest; клиентские значения служат только preview.
- Для массовой операции нужны ограничение размера партии, progress и результат по каждому товару. Повторный submit не должен дважды применять один batch.
- Отсутствующий Shopify-ресурс, неверная привязка магазина, недоступная локаль и нехватка scope — отдельные ошибки, не «конфликт значений».
- Модалки образуют управляемый стек: только верхняя активна для фокуса и Escape; при возврате фокус попадает на действие, открывшее слой. Текущий `AnimatedModal` потребуется проверить/доработать для двух одновременных слоёв.
- Статусы, tooltip и выбранная сторона доступны клавиатурой и screen reader; анимация уважает reduced motion. Цвета и количество полей различимы без цвета.

## Решения, требующие проверки при реализации

1. Текущий commerce-preview и переводной field-level reconcile дают разные виды расхождений. Единая карточка должна связывать их по product ID и показывать происхождение каждого поля, не смешивая shared и локализованные значения.
2. Нынешние `pushSingleProductToShopifyAction(..., true)` и `pullSingleProductFromShopifyAction(..., true)` не являются достаточным контрактом для смешанного выбора по полям. Нужен scoped apply с проверкой перед записью и результатом по полям; «полностью переписать» допустимо обещать только для реально покрытых полей.
3. Индикатор непросмотренного обновления требует отдельного persisted watermark (`productId`, `admin identity`, `applied version`, `viewed version/time`), а не клиентского `localStorage` или `reviewedAt` перевода.

## Критерий готовности UX

Администратор находит конфликт из обоих сигналов, различает `PT`, `RU` и `Общее`, может решить товар целиком или поля отдельно, видит последствия до записи, отменяет любой preview без потери выбора, получает достоверный результат и после входящего обновления видит, какие товары ещё не открыл. Добавление следующего языка в реестр не требует правки интерфейса разрешения конфликтов.
