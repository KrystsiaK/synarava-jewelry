## Что мы нашли

1. **REL-008 (высокий, новый)** — на хабе Mission Control счётчики заказов ищут темы `ORDERS_PAID` / `ORDERS_CANCELLED`, а вебхуки пишут `orders/paid` / `orders/cancelled`. Успешные доставки **не считаются** (всегда 0); хаб может показать «down» зря.
2. **REL-001 / REL-002 (высокий)** — вебхук продуктов: кривой JSON → бесконечные ретраи Shopify; плюс небезопасный разбор больших id (как DEAD-001).
3. **REL-003 (средне)** — без заголовка id доставки вебхук не дедуплицируется.
4. **REL-004 (средне)** — cron collector без «аренды».
5. **REL-005 / REL-009 / REL-010 (средне)** — throttle только в процессе; клиент SKU без timeout; очистка истории синка только «по пути» catalog check.
6. **REL-006 (политика)** — в истории были DROP-миграции; новые — только с runbook.
7. **REL-007** — пути скриптов бэкапа в runbook совпадают с репо (ок).

## Что это значит для бизнеса

- **Счётчики заказов на хабе сейчас врут** (нулевой paid/cancelled при живых вебхуках) — нельзя опираться на зелёный/красный статус orders без фикса REL-008.
- Вебхуки = актуальность остатков/каталога; ошибки parse = шторм ретраев.
- Collector без замка = риск гонок статуса / лишних Telegram.
